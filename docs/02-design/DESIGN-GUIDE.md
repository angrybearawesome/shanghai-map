# 상하이 여행 지도 — 디자인 가이드 (UI 설계 원칙)

> 화면·기능을 만들거나 고칠 때의 판단 기준. 새 UI 요소를 추가하기 전에 이 문서를 통과시킨다.
> 근거: 저장소 코드(`public/index.html`)·설계 문서(`docs/02-design/trip-plan.design.md`)·
> 2026-08-07 계획 탭 스크린샷 실측. QA 대시보드 제품의 리디자인 회고에서 확립된 원칙을
> 이 앱의 실제 구조에 맞게 번역했다.

## 0. 진단 방법 — 화면을 고치기 전에 묻는 3가지

1. **이 화면의 첫 질문이 무엇인가?** 사용자가 이 화면을 열 때 가장 먼저 알고 싶은 것 하나.
2. **지금 그 답을 사용자가 조립하고 있나?** 화면 여러 곳의 정보를 머리로 합쳐야 답이 나오면 위반.
3. **같은 화면을 반복해서 고치고 있나?** 배치 조정이 계속 필요하면 요소 위치가 아니라
   층 구조(요약 → 진단 → 상세)가 없는 것이다.

## 1. 이 앱의 구조적 사실 (원칙의 전제 — 코드로 확인됨)

- 생애주기 3단계를 탭·기능이 분담한다: **계획**(출발 전, 계획 탭) → **기록**(여행 중, 방문
  기록) → **루트**(사후, 일일 루트). 계획 탭은 출발 전 도구다 — "오늘" 개념이 없고 일차는
  상대 번호다(설계 문서 명시).
- 지도 핀 번호는 **불변 장소 id**다(삭제해도 재정렬 없음 — 방문 기록 보호). 계획 스톱
  순번과 다른 체계인 것은 의도된 설계다. 연결은 순번 배지의 그룹색 + 클릭 시 지도 이동.
- 핀 시각은 이미 시맨틱하다: 채워진 핀 = 확정 좌표 / 점선 핀 = 수백 m 오차 / 목록만 =
  좌표 미상. `actionsFor()`가 신뢰도에 따라 기본 동작까지 바꾼다.
- 베이스맵은 래스터 타일(autonavi, OSM 폴백) — **POI 아이콘을 끌 수 없다** (이미지에
  구워짐). 조정 수단은 CSS 필터(채도·밝기)뿐.
- 노란 태그(`MJ · 8/7`)는 공유받은 일차의 출처 표시다.
- 자동 추정값은 저장하지 않고 렌더링 때마다 계산한다(원본 데이터와 파생 값의 분리).

## 2. 원칙

1. **첫 질문 우선** — 화면(탭)마다 첫 질문을 정의하고 그 답이 처음 보이게 한다.
   계획 탭: "이 일정, 순서와 이동이 무리 없나". 지도 탭: "내가 표시한 곳이 어디 있나".
   메타 정보(사용법 안내·데이터 출처)는 첫 질문의 답보다 위에 두지 않는다.
2. **단계에 맞는 화면** — 계획(사전)·기록(중)·루트(사후)는 첫 질문이 다르다. 한 화면에
   다른 단계의 UI를 섞지 않는다. 새 기능은 어느 단계 소속인지부터 정한다.
3. **요약 → 진단 → 상세 3층** — 일차 헤더가 요약("3곳 · 이동 1시간 10분"), 스톱·구간
   행이 진단, 장소 카드가 상세. 밀도를 없애지 말고 선택제로 만들고, 접힘 상태는 기억한다.
4. **표시된 것은 전부 진입점** — 핀·순번 배지·거리 칩·장소명은 누르면 반응해야 한다
   (지도 이동·상세·필터 중 하나). 누를 수 없는 정보는 존재 이유를 다시 묻는다.
5. **빈 강조 금지** — 값 없는 자리에 눈에 띄는 플레이스홀더를 반복하지 않는다. 미입력
   시간은 흐리게, 입력된 값만 진하게. 비교 대상이 없으면 알림·배지를 만들지 않는다.
   (단, 계획 탭은 편집 도구다 — 입력 어포던스는 남기되 시각 무게만 낮춘다.)
6. **숫자에는 근거를** — 추정치(직선거리 기반)와 입력치(수동 leg)는 구분해 표시하고,
   추정의 가정은 사용자가 찾을 수 있는 곳(지도 안내)에 적는다. 계산 로직을 바꾸면 안내
   문구도 같은 커밋에서 바꾼다. — 이미 잘 지켜지고 있는 원칙. 유지가 목표.
7. **내 데이터가 주인공, 베이스맵은 배경** — 내 핀·동선이 베이스맵 소음 위로 떠야 한다.
   POI를 끌 수 없으므로 수단은 타일 CSS 톤다운(채도↓)과 내 핀의 대비 강화다.
   색의 축을 섞지 않는다: 신뢰도 = 테두리 스타일(실선/점선), 그룹/일차 = 색.
8. **읽기와 편집의 분리는 "출처"로** — 계획 탭은 편집 도구라 컨트롤 상시 노출이 기본값.
   단, 공유받은 일차는 열람이 주 용도이므로 편집 컨트롤을 낮출 후보다.
9. **형태는 읽기 과제로 결정** — 순서 = 세로 타임라인, 위치 = 지도, 실행 가능성 = 배지.
   모션은 정보를 가리키는 최소한으로(왕복·반복 애니메이션 금지).

## 4. 이미 잘하고 있는 것 (지킬 자산 — 형태가 바뀌어도 유지)

- 구간 이동 정보 인라인("4.1km · 지하철 20분 · 택시 20분") + 장거리 정직 경고("고속철 확인")
- 여유/부족 배지 (계획 간격 vs 소요 시간 비교)
- 수동 입력과 자동 추정의 구분·우선순위, 추정치 비저장(렌더링 시 계산) 철학
- 핀 신뢰도 3단계 체계 + 범례 + 신뢰도별 기본 동작 분기
- 푸터 아코디언의 계산 근거 문서화 ("점선은 직선일 뿐 실제 경로 아님" 등)
- 서버 없는 공유(URL 해시)와 스냅샷 의미의 명시
- `tools/verify.mjs` 자동 검증 — UI 변경 시 여기부터 갱신

## 5. 리디자인 진행 규칙

- **단일 파일 원칙 유지** — 시각 변경도 `index.html` 안에서, CSS 블록을 구분해 되돌리기
  쉽게 (블록 단위 주석 경계).
- 구 버전을 "실패"로 규정하지 않는다 — 한계에 도달한 지점과 물려받을 자산을 함께 적는다.
- 변경 전후는 `npm run verify` + 실제 데이터 렌더로 확인한다. 경계 케이스: 계획 없음 ·
  1일차만 · 좌표 없는 스톱만 · 공유받은 일차만.
